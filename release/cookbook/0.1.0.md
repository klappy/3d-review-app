# Release record — 0.1.0

Canonical release record for the 3D Review app (Keep-a-Changelog shape, SemVer 2.0.0). The app pins this file and `releases.json` at an immutable cookbook commit in `release/release-manifest.json`; the app never authors its own changelog. `status: candidate` until root tags `v0.1.0` and commits the second cookbook record (C2: `released`, `tag`, `date`) in one receipt.

## [0.1.0] — candidate

### Added
- Shared survey link: an owner can issue one link per survey that participants open to take the survey without a personal code.
- Release identity: a cookbook-pinned release record, a build-time version+commit stamp, version fields on health and MCP serverInfo, and a generated changelog.json for the version badge.

### Changed
- Health `build` now reports `<version>+<sha7>` derived from the pinned release record and the build commit instead of a hardcoded literal.
- Rate limiter boundaries and OAuth flows hardened for the first DEV collection increment.

### Fixed
- Email-code redemption is atomic; a code cannot be redeemed twice under concurrent requests, and conflict-recovery kinds are distinct.

### Security
- Rate-limited anonymous, code and bearer paths fail closed with RATE_LIMITED; OAuth code redemption is single-use.

## Major-zero compatibility policy

While the version is 0.y.z there is no API/MCP compatibility promise across MINOR versions. PATCH means no contract row, schema or accepted-behaviour change. MINOR means an additive contract row, an additive migration, a new capability, or a changed accepted behaviour. The first 1.0.0 is the captain's call at the full-product gate. A change is classified by its compatibility impact, not by where the work originated (planned feature or hotfix). The tag step is one receipt by root: `git tag v<version>` on the accepted release merge SHA plus the cookbook C2 record (`released`, `tag`, `date`); no app change is needed to record it.
