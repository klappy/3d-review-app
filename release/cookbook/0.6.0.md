## Compatibility and acceptance boundary

MINOR under the documented pre-1.0 policy: provider identity changes to `cloudflare`, native `EMAIL` binding replaces API-key configuration, and provider failures use binding semantics. Existing mail result fields and state union remain; the optional HTTP status is absent/null rather than fabricated. No new public capability, auth behavior, database migration or UI redesign.

The app calls the structured sending binding once. A message ID indicates acceptance only, not inbox arrival. Explicit documented refusals stay refused; internal/unknown failures, malformed responses and the eight-second deadline stay unconfirmed, without retry. The binding cannot be cancelled and has no documented provider idempotency guarantee. An intent correlation header does not promise deduplication; existing handler intent guards and uncertain-invitation lifecycle remain the protection. The pre-existing stale-pending crash window is unchanged and no exactly-once delivery is promised.

Acceptance requires adapter tests with a stubbed native binding, existing local invitation lifecycle regressions, typecheck, independent exact-head review and terminal release checks. No real recipient, live email or production delivery is claimed by those tests. Sending-domain onboarding and DNS readiness are separately owned infrastructure evidence. DEV's recipient hash allowlist starts empty and requires explicit recipient authorization before any send. Tests never use a remote sending binding.

Ship through main and DEV first. Production then promotes the same validated semantic version, canonical pin and product source through its separate PR. This candidate is not a deploy receipt or permission to bypass review/checks.
