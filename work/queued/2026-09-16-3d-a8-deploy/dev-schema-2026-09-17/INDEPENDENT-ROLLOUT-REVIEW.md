## P1 — rollback must preserve security behavior after shared traffic

The old runtime's explicit-column INSERT establishes forward schema compatibility before promotion. It does not establish safe rollback after new shared contexts exist. At app baseline `10f5f444d68475d7114ab8fe0bf269fe106476b1`, `src/auth.ts:28` authenticates participant_session using its own expiry/revoked_at without linked-invitation validity. The old form/submit/receipt handlers do not inspect invitation_id or shared_response_claim. A still-live shared bearer whose invitation has subsequently been revoked can regain receipt/submission authority if that old runtime is restored. Old submission also lacks the new atomic shared-claim guard; its existing-response check is not the new concurrency protection.

Amend rollback to distinguish two states: before shared runtime traffic, the verified old explicit-column runtime may continue with additive schema; after shared contexts or responses exist, rollback may target only an independently verified runtime preserving shared link/session validity and atomic one-response semantics (and applicable Auth security). Otherwise keep participant traffic/writes quiescent and obtain reviewed forward recovery. Preserve all data; no downmigration, token rewrite, or Time Travel restore is authorized. Merely naming a previously deployed version as compatible is insufficient.
