## Exact fixture contract
The external fixture envelope contains synthetic identityKey, route, assessmentId/surveyId when applicable, integer epoch, shellModel, viewModel. These are test envelope fields, not a new production schema. shellModel uses current K1 explicit visible nodes, safe hrefs, role labels, context and allowed actions. viewModel uses current K2 screen/status/context/view/actions/items/report/interaction fields only.

Cases: owner/member/viewer/direct-grant; direct grant omits inaccessible ancestors. Project and assessment Collect/Understanding views; loading/empty/unauthenticated/refused/error plus ready. Report eligibility held/missing/eligible. Pending/uncertain/confirmed-with-explicit-receipt remain distinct. Fields contain synthetic text, never real identities or credential-shaped fixtures. No invented invitation denominator or successful receipt.

Fixture adapter only maps these fixed objects into mountShell/mountCoordinatorView and captures callbacks to an in-memory assertion log. Every captured callback closes over identityKey+route+epoch and rejects delivery after any changes or destroy. An old mounted node or deferred synthetic result cannot target the new model. Item contexts remain distinguishable; actions require explicit allowed:true and supported action IDs. No inference from role label. Denied/stale intents do not enter the log. Simulated outcomes are explicitly fixture messages and never represented as backend receipts.

No actual API transport exists. Browser interception must be installed before navigation in an empty isolated context. It fulfills only a literal allowlist of fixture document and pinned local module/style GETs at a synthetic loopback origin; it aborts every other request, especially all writes and nonlocal origins. There is no server port or live endpoint. Probe unknown-local and nonlocal POST and assert rejection; any unexpected request fails. No persistent storage reads/writes, provider requests or real login.
