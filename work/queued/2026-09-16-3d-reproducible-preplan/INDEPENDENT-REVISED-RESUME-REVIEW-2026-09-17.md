# Recheck of Auth revised ruling5708838624

**AMEND, narrowly.** The revision resolves the principal P1: no automatic second open, no inference from a missing submitted marker, and preserved old context on refused resume. API remains unchanged. Exact reviewed text: https://github.com/klappy/3d-review-cookbook/issues/16#issuecomment-5708838624. This is a ruling review, not acceptance of preliminary UI485914b or its tests.

Four small clarifications are still needed before representing the entire revision as accepted implementation scope:

1. **Restart is optional recovery, not a mandatory new feature.** State explicitly that the minimum accepted correction is truthful cannot-resume refusal with no automatic new context. A fresh-response action may be included only if Design/root confirm it fits the accepted recovery scope; it does not reactivate deferred Next. Without that confirmation, disposition the Bugbot defect through truthful refusal rather than inventing scope.
2. **Require the actual raw link token.** Explicit restart can call new-open only when the original token is available in current memory from the original link. A fragment-free reload has a namespace digest/bearer but cannot recover the raw token. Do not reverse the digest, reuse a different link, or persist raw link credentials to make the action work. If unavailable, keep refusal and direct the participant to reopen the original invitation. An action lacking this prerequisite must not be presented as executable.
3. **Define the successful identity switch precisely.** On refused new-open or transport/parse failure, preserve the old bearer/key/draft and in-memory client identity. On a valid successful new-open, atomically from the UI's perspective replace the old bearer with the returned new bearer; invalidate the old submit key in both storage and any in-memory form/request state before enabling new submission. Do not accidentally delete the newly stored bearer while “discarding the old bearer.” If storage is unavailable, do not fall back to the old key/context. Retained draft restoration is an explicit offer after a freshly fetched matching template/version, not a replay. No receipt continuity claim.
4. **Keep uncertainty and error categories visible.** Copy must make clear that a previous send may have succeeded even without confirmation, and a fresh response could duplicate it; “if you already sent” alone can be misread as “if you saw success.” Do not collapse every failed explicit open into permanent unavailable. NOT_FOUND_OR_NOT_VISIBLE supports neutral inability to open, STAGE_CONFLICT preserves closed-state handling,429 remains temporary rate limiting, and transport/5xx/parse failures remain temporary or uncertain. Never erase old state on those failures. A fresh-open transport failure may itself have created an unused context; do not claim no creation occurred.

Suggested bounded disposition text for Auth/Design: “ACCEPT truthful cannot-resume state, retention of original context and no automatic fresh open. An explicit restart is optional within separately confirmed recovery scope and requires the actual original link token. Preserve old context on failure; switch to the returned context and fresh key only after valid success. Explain unknown prior submission outcome and handle closure, rate limit and transient errors according to their actual category. No marker proves completion, expiry or link status; API and deferred Next are unchanged.”

Focused review additions: reload without fragment/raw token; successful new-open replaces rather than clears new bearer; old in-memory key cannot reach new submit; failed/429/closed/transport new-open preserves old context; lost prior submit reply remains explicitly uncertain. Existing API24fc0bbc36 and UI23699 source evidence from the prior independent report remains the basis. No implementation, tests, Git/comment/shared-journal writes or provider mutation performed.
