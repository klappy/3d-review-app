### Hunk 2 — confidential AES-GCM cursor — **ACK WITH CONDITIONS**

Supersession is accepted: confidentiality of held identifiers beats the readable-HMAC proposal, and `src/code-escrow.ts:16-46` is an in-repo precedent for exactly this construction (HKDF-separated key at :19-24, random 12-byte IV at :34, tuple AAD at :30-31, single non-oracle failure at :42-45). Reuse that pattern rather than inventing a second one. Domain separation holds: today `SESSION_SECRET` is used only as a raw HMAC key (`receipt.ts:45-51` for `cfm_`, `oauth.ts:50/56` for the park MAC); an HKDF-SHA256 derivation with salt `3d-report-cursor-v1` / info `report-list.v1` is disjoint from both. AES-GCM and HKDF are both available in workerd `crypto.subtle`, as `code-escrow.ts` already proves in production code.

Conditions:

1. **AAD must bind actor and assessment, not just the domain.** Plan §"Cursor" currently sets AAD `report-list.v1`. Change to the `code-escrow.ts:30` shape — `enc.encode(JSON.stringify(["report-list.v1", actor, assessmentId]))` — so a cross-actor/cross-assessment token fails in the AEAD tag rather than in an application `if`. Keep the in-plaintext `actor`/`assessmentId` equality checks as defence in depth.
2. **Derive from raw secret bytes and refuse an unconfigured secret.** Use `enc.encode(env.SESSION_SECRET)` as HKDF IKM; do **not** route through `code-escrow.ts:9-15` `keyBytes`, which requires a 32-byte base64url secret and would throw for a valid `SESSION_SECRET`. Empty/absent `SESSION_SECRET` must refuse (no derivation from `""`).
3. **Own TTL constant.** Plan must not reuse `CONFIRM_TTL_SECONDS` (`src/receipt.ts:6`, flagged there as open item 18-D/D-2). Declare `REPORT_CURSOR_TTL_SECONDS = 300` in `src/report-cursor.ts` so a later confirm-TTL change cannot silently move cursor lifetime.
4. **One indistinguishable failure.** Every reject cause (bad prefix, >4096 bytes, bad base64url, short nonce, tag failure, wrong AAD, unknown/missing field, expired, excessive future exp, actor/assessment/tuple mismatch) must return a single fixed `INVALID_PARAMS` message with no `hint` variance and no `data`. Plan §"Cursor" lists the causes but not the single-message requirement — add it, or B2 will build an expiry-vs-tamper oracle.
5. **`cursor` is not in the redaction regex.** `src/receipt.ts:234` `REDACT_KEYS` does not match `cursor`, so any span logging a cursor would persist it verbatim to `trace`. Either add `cursor` to `REDACT_KEYS` at `receipt.ts:234` or have the plan state as a tested invariant that no span, log or error ever carries the token or `afterId`. I prefer both.
6. Keep the plan's explicit "cursor validation grants no authority" — the same-observation query must always follow, and a valid cursor with lost grant returns `notVisible`, never `INVALID_PARAMS`.
7. Noted, non-blocking for Auth but it belongs in the resource record: there is no `CAP_LIMITER` entry for `cap.report.build` (`src/ratelimit.ts:35-40`), so `dispatch.ts:46` applies only the anon/MCP ceilings to a render-plus-rerender write. Plan §"Resources" should record that as an accepted risk or add a limiter under independent review.

B2/API must still verify: 96-bit nonce uniqueness across a page walk, replay of a cursor after grant revocation, secret-rotation invalidation, byte bound applied *before* decode, and that no response, receipt, trace or log field anywhere contains a report id, `afterId` or count.
