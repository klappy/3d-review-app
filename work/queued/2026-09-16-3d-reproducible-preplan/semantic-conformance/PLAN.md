## Required invariants versus changeable choices

Keep these distinctions inside existing architecture/domain/contract/constraint/design documents, using ordinary prose/tables rather than inventing another specification framework:

- Product/security invariants include intentional authorized sharing; source-faithful questions/answers; participant isolation; no credential disclosure; no fabricated success; one committed response per accepted context; stable response identity on a valid exact retry; revocation/expiry enforcement; preserved historical data; explicit scopes; truthful outcome uncertainty. User-facing shared participation does not require participant accounts or codes.
- Current agreed contract choices include concrete HTTP operations and envelopes, error meanings, idempotency rules, role/class/confirmation gates, session/link lifetimes, collection state transitions and source/template identity. These are binding for their accepted version but may change through an explicit compatibility decision; they are not eternal platform axioms.
- Current implementation choices include framework, module layout, storage engine, token encoding, hash/storage mechanism, serializer/build tooling and provider library version. Where a choice is itself an accepted security or interoperability constraint (for example hashed credential storage, OAuth/PKCE or agreed rate limits), retain the constraint and classify its role accurately; do not demote it to an optional detail. A future replacement needs proof of the affected properties and any migration/compatibility effects, not identical code.
- Operational choices/rulings currently bind main to existingDEV, production branch to production, staging only if needed later, and separately reviewed production promotion. They can evolve only under applicable authority; specification flexibility is not permission for unreviewed provider changes.

## Adaptation procedure using existing homes

For a proposed single or combined change, record the actual changed decision in09 (or its existing owning spec), what it supersedes, and affected user/agent/operational outcomes. Follow existing links to03 schema,04/18-A contracts,16 constraints,06/18-E/18-F/design-system and04/18-I acceptance. Classify preserved invariants, intended behavior changes, compatibility impact and unresolved authority. Combined changes get a combined interaction scenario where they meet; independent module tests alone are insufficient.

Illustrative challenge, not an ordered product change: replacing storage/framework should preserve isolation, atomic response commitment and private replay while allowing different files and technology. Changing link lifetime alters session validity and recovery expectations and may require existing-session compatibility/migration decisions. Changing both requires tests at the expiry/concurrent-write boundary. Requirements that remain unchanged keep their authority; evidence tied to an altered mechanism may need rerun. API/schema/source-policy changes may require a version or data migration decision. Never infer automatic safety from “only technical” or automatic permission from cookbook editability.

No new uniform metadata schema, generator or template library is needed. Use existing document decisions, tables, receipt pointers and version practices. Author presents exact changes and impacted acceptance; independent reviewer challenges semantics, security, compatibility and completeness. Root accepts scope/version through existing gates. No new human confirmation for ordinary agreed docs reconciliation; a genuinely unresolved source/policy/public-API compatibility decision goes to its existing owner/root for the applicable authority, never silently invented.
