## Versioning (release identity)

Ticket `2026-09-17-3d-release-identity` (kitchen). The app does not author its own version or changelog; it builds against an accepted cookbook release record and proves the chain at build time.

- **Authority chain:** cookbook `planning/2026-09-16-parity-build/releases/<version>.md` + `releases/releases.json` at an immutable commit → app `release/release-manifest.json` (`version`, `cookbook_commit`, per-record git `blob_sha` + `sha256`) with byte copies under `release/cookbook/` → `package.json` `version` and both `package-lock.json` `version` fields (validated, never authored; a mismatch fails the build) → git-ignored `src/version.generated.ts` (re-exported by tracked `src/version.ts`) → health `version`/`build`/`commit`/`build_uuid`/`release_source`, MCP `initialize` `serverInfo.version`, and git-ignored `ui/changelog.json` served by Assets. The `release/` directory holds only these pins and the historical control-plane artifacts; nothing in it is a second version authority.
- **Hook sequence:** `pretypecheck`, `pretest` and `predev` run `npm run stamp` (`scripts/stamp-version.mjs`, Node stdlib only), so the existing Workers Builds command `npm ci && npm run typecheck && npm test` regenerates the stamp on every build without a trigger change. For direct tool use (e.g. `npx tsc`, `npx vitest`, `wrangler dev` outside npm) run `npm run stamp` first. The commit sha comes from `WORKERS_CI_COMMIT_SHA` when `CI=true` or `WORKERS_CI=1` (absent or malformed → exit 1, never a fabricated sha), otherwise `git rev-parse HEAD`; `WORKERS_CI_BUILD_UUID` becomes `build_uuid` when present. These variables exist at build time only.
- **Roadmap versions (captain ruling 2026-09-25 18:20, R1a):** run `node scripts/roadmap-versions.mjs` from the repo root after `release/cookbook/releases.json` is updated; commit the regenerated `ui/roadmap/versions-data.js` in the train — its `current` must equal the version shipped (the script prints `current <version>`).
- **Meanings, kept distinct:** `version` ≠ `commit` ≠ tag. Several `0.1.0+<sha7>` DEV builds may precede the single `v0.1.0` tag. Health `source_sha` is the contract pin (cookbook 04); `release_source` is the release-record commit; `commit` is the app code. `build` changed from a literal to `<version>+<sha7>`; `contract`, `source_sha`, `deps`, `capabilities` are unchanged.
- **Status and the tag step:** `status` in the record is a build-time fact from the pinned revision — the running version is `candidate` until root, after DEV acceptance, performs the tag step as one receipt: `git tag v<version>` on the accepted release merge SHA plus the cookbook C2 record (`released`, `tag`, `date`). No app-only status bump exists; no app change is needed to record a release.
- **Review gate:** before merge, an independent reviewer with a cookbook checkout runs `git rev-parse <cookbook_commit>:<path>` for both records and confirms equality with the manifest `blob_sha` values; `test/version-stamp.test.ts` proves package == lock == manifest == generated == health == MCP and recomputes both blob ids and sha256s from the byte copies.
- **Badge cost (rev 3b I-6):** one anonymous GET /v2/health per page load spends 1/60 of the per-address RL_HTTP_ANON bucket and never touches the participant's authenticated submit; a 429/503 on health renders 'Version unavailable', never an error.
- **Bumps:** classified by compatibility impact (PATCH: no contract row/schema/accepted-behaviour change; MINOR under 0.y: additive row/migration/capability or changed accepted behaviour; `1.0.0`: captain's call), recorded in the cookbook first, then pinned here. See the policy paragraph in `release/cookbook/0.1.0.md`.
- **B2/B3 script exit codes** are meaningful as of [klappy/3d-review-app#38](https://github.com/klappy/3d-review-app/pull/38); earlier green tables are inventory, not acceptance. Cite `PASS=a FAIL=b RESERVED=c SKIP=d` and `same=S/compared=C excluded=E`, never a bare table.
