# Release procedure

## Current release checklist

Use one release receipt for one frozen increment. The end-to-end owner follows it through DEV and the separate production promotion; a handoff names the next owner and remaining action. Follow live [cookbook HYGIENE §10](https://github.com/klappy/3d-review-cookbook/blob/main/HYGIENE.md#delivery-and-session-continuity), [kitchen HYGIENE §§19, 27, 32 and 37](https://github.com/klappy/kitchen/blob/main/health-code/HYGIENE.md), [merger §4](https://github.com/klappy/kitchens/blob/main/boarding/runners/merger.md#4--each-pr-oldest-first) and [COMMON](https://github.com/klappy/kitchens/blob/main/boarding/manifests/COMMON.md#github-identity-by-action-every-seat).

1. **Freeze scope and authority.** Read the owned work unit, current candidate/head and its explicit authorization and hold disposition in [cookbook issue 14](https://github.com/klappy/3d-review-cookbook/issues/14) and the linked receipt. Keep unrelated discoveries in the existing backlog. The September corrective hold is preserved [below](#historical-corrective-hold-and-cutover-evidence); later scoped dispositions apply only to the candidates and environments they name. Neither historical hold text nor this checklist substitutes for that current decision. No blanket lift is recorded here.
2. **Bind source evidence once.** Record the exact validated DEV source, semantic version and canonical release pin. Promote that same product source/version through a separate PR to `production`; actual fixes pass through `main` and DEV first. Reuse exact unchanged-source verification evidence with its SHA, scope and results; review the actual delta and any environment effects. Repeat checks for changed code, failures or unresolved concerns, while satisfying every check required on the current head. Source equivalence does not establish production environment readiness.
3. **Send ready work to the existing fresh reviewer immediately.** Do not wait for a scheduled sweep. Apply the [current review gate](#current-review-gate), including native review evidence and required role/security review. Require real independent `klappy-agents` GitHub approval on the current head and resolve findings. Under merger §4.5, an existing verified current-head independent approval and fresh verdict need no duplicate review. An old-head approval never counts; a moved head receives fresh review.
4. **Close the merge gates.** All attached checks finish, applicable required checks pass, and findings/adverse results have dispositions. The fresh nonauthor merger retains H27's separate plain `YES` comment. Read candidate-specific authorization, holds and external prerequisites. 3D's topology is `main` → DEV and `production` → production; without staging, H32/37 supply no automatic production authority. Production requires explicit applicable authority, not an inferred waiver or a new approval invented by this checklist.
5. **Merge through the ordinary protected path.** Trigger the existing fresh merger when ready. Immediately re-read head, checks, reviews, authority and effective rules; use the verified non-bypass execution identity, a merge commit and the exact reviewed head pin. A denial stops that action and is reported with its owner; never route around it.
6. **Observe the connected deployment.** Match merge SHA → canonical push-event build → active deployed Worker version. Verify actual runtime identity (`version`, `commit`, `build_uuid`, `release_source`), assets and the affected API/MCP/browser smoke on the named environment. DEV evidence and unchanged source do not replace production identity and smoke. No seat deployment, manual build dispatch or migration/seed replay.
7. **Close the same receipt.** Use the [production follow-through fields](#production-follow-through-receipt) and cookbook §10 status columns. Name any remaining prerequisite, owner and next action. An accepted increment does not wait for unrelated work. A documentation change or green source suite alone does not demonstrate an end-to-end release or a 30-minute release time.

Apply live [cookbook HYGIENE §10](https://github.com/klappy/3d-review-cookbook/blob/main/HYGIENE.md#delivery-and-session-continuity) and [merger §4.2](https://github.com/klappy/kitchens/blob/main/boarding/runners/merger.md#4--each-pr-oldest-first): an independent fresh agent reviews the exact head with `/code-review` at medium effort (or the authorized ultracode workflow), adding `/security-review` for auth, data, secrets or external calls. All attached checks must finish; every applicable required check must pass at that head; missing, skipped, errored or pending required checks remain blockers. Record dispositions for adverse results and review findings and re-read the head and checks before merge. A missing optional Bugbot check does not block this replacement review, and must not be fabricated. If a real optional Bugbot run or finding is present, apply merger §4.2 rather than silently discarding it. This review replacement does not lift any recorded hold, production gate, ownership constraint or release prerequisite below.

Fable owns auth/contract coordination; remote schema/data work needs its actual claim and authority.

The current user standing rule in cookbook HYGIENE §10 supersedes the earlier HYGIENE 19 requirement for a promotion-only semver bump. One successful slice or health response cannot close it.

## Versioning (release identity)

Ticket `2026-09-17-3d-release-identity` (kitchen). The app does not author its own version or changelog; it builds against an accepted cookbook release record and proves the chain at build time.

- **Authority chain:** cookbook `planning/2026-09-16-parity-build/releases/<version>.md` + `releases/releases.json` at an immutable commit → app `release/release-manifest.json` (`version`, `cookbook_commit`, per-record git `blob_sha` + `sha256`) with byte copies under `release/cookbook/` → `package.json` `version` and both `package-lock.json` `version` fields (validated, never authored; a mismatch fails the build) → git-ignored `src/version.generated.ts` (re-exported by tracked `src/version.ts`) → health `version`/`build`/`commit`/`build_uuid`/`release_source`, MCP `initialize` `serverInfo.version`, and git-ignored `ui/changelog.json` served by Assets. The `release/` directory holds only these pins and the historical control-plane artifacts; nothing in it is a second version authority.
- **Hook sequence:** `pretypecheck`, `pretest` and `predev` run `npm run stamp` (`scripts/stamp-version.mjs`, Node stdlib only), so the existing Workers Builds command `npm ci && npm run typecheck && npm test` regenerates the stamp on every build without a trigger change. For direct tool use (e.g. `npx tsc`, `npx vitest`, `wrangler dev` outside npm) run `npm run stamp` first. The commit sha comes from `WORKERS_CI_COMMIT_SHA` when `CI=true` or `WORKERS_CI=1` (absent or malformed → exit 1, never a fabricated sha), otherwise `git rev-parse HEAD`; `WORKERS_CI_BUILD_UUID` becomes `build_uuid` when present. These variables exist at build time only.
- **Roadmap versions (captain ruling 2026-09-25 18:20, R1a):** run `node scripts/roadmap-versions.mjs` from the repo root after `release/cookbook/releases.json` is updated; commit the regenerated `ui/roadmap/versions-data.js` in the train — its `current` must equal the version shipped (the script prints `current <version>`).
- **Meanings, kept distinct:** `version` ≠ `commit` ≠ tag. Several `0.1.0+<sha7>` DEV builds may precede the single `v0.1.0` tag. Health `source_sha` is the contract pin (cookbook 04); `release_source` is the release-record commit; `commit` is the app code. `build` changed from a literal to `<version>+<sha7>`; `contract`, `source_sha`, `deps`, `capabilities` are unchanged.
- **Status and the tag step:** `status` in the record is a build-time fact from the pinned revision — the running version is `candidate` until root, after DEV acceptance, performs the tag step as one receipt: `git tag v<version>` on the accepted release merge SHA plus the cookbook C2 record (`released`, `tag`, `date`). No app-only status bump exists; no app change is needed to record a release.
- **Review gate:** before merge, an independent reviewer with a cookbook checkout runs `git rev-parse <cookbook_commit>:<path>` for both records and confirms equality with the manifest `blob_sha` values; `test/version-stamp.test.ts` proves package == lock == manifest == generated == health == MCP and recomputes both blob ids and sha256s from the byte copies.
- **Badge cost (rev 3b I-6):** one anonymous GET /v2/health per page load (no app rate limit since captain 2026-10-16); a 429/503 on health renders 'Version unavailable', never an error.
- **Bumps:** classified by compatibility impact (PATCH: no contract row/schema/accepted-behaviour change; MINOR under 0.y: additive row/migration/capability or changed accepted behaviour; `1.0.0`: captain's call), recorded in the cookbook first, then pinned here. See the policy paragraph in `release/cookbook/0.1.0.md`.
- **B2/B3 script exit codes** are meaningful as of [klappy/3d-review-app#38](https://github.com/klappy/3d-review-app/pull/38); earlier green tables are inventory, not acceptance. Cite `PASS=a FAIL=b RESERVED=c SKIP=d` and `same=S/compared=C excluded=E`, never a bare table.
